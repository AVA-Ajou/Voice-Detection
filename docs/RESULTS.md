# 측정 결과

2026-08-12 학습분(`adapter-gemma4/`) 기준. 재현 방법은 각 항목에 적어둔다.

이전 모델(`adapter/`, Gemma 3 4B)의 수치는 비교용으로 남긴다. **모델은 절반 크기, 학습은
절반 시간, 성능은 전 항목에서 같거나 낫다.**

```
                        Gemma 3 4B      Gemma 4 E2B
AUROC                     0.9998          0.9998
ECE                       0.006           0.003      ← 절반
재현율                     98.1%           99.1%      ← 미탐 2건 → 1건
오탐률                     0.0%            0.0%
```

갈아탄 진짜 이유는 성능이 아니라 **오디오**다. Gemma 4는 음성을 직접 받으므로 통화 전사에
쓰던 Groq Whisper를 버릴 수 있다 — 판정과 전사를 같은 모델 하나가 한다.

## 이 작업의 존재 이유 — 정규식을 넘었는가

옛 방식은 정규식 19개로 신호를 찾아 위험도를 합성했다. 정규식이 놓친 통화를 모델이 건지지
못하면 파인튜닝을 할 이유가 없다.

```

      id          정규식   Gemma 3   Gemma 4
 vishing_120         6      99.9      99.9   ✓   ← 정규식이 19개 패턴 중 하나도 못 걸림
```

`vishing_120`은 `"조사 과정에서… 제3자의 인물이 없는 곳에서 통화 좀 부탁드리겠는데요"`처럼

하나도 걸리지 않았다. **정규식은 글자를 보고 모델은 뜻을 본다.**

## 전사 (Gemma 4에서 새로 생긴 것)

어댑터를 끈 원본 Gemma 4에 음성을 그대로 물린다. 판정과 같은 모델·같은 프로세스라 서버에
모델을 하나만 올리면 된다.

```
demo_call.m4a (25초)  →  맥 MPS에서 9.9초
```

기준선이던 Groq Whisper와 견줘 `"명의/명예"` 구간을 더 정확히 들었다. 앱에서 실기기 경로로
돌린 통화 한 건은 24.7초 걸렸다(에뮬레이터가 GPU를 나눠 쓰는 상태).

**측정한 것은 소수 사례다.** WER을 잰 것이 아니라 몇 건을 눈으로 대조했을 뿐이다.

## 진단 — 오탐률 0.0%가 뜻하는 것

**0.0%는 지표가 좋은 게 아니라 시험이 쉬운 것이다.** 학습·검증 1,417건을 "돈 얘기가
나오는가 × 기관이 먼저 걸었는가"로 갈라보고 알았다.

```
                 금융 어휘 ∩ 기관이 먼저 건 통화
   피싱 706건         204건 (29%)
   정상 711건           6건 ( 1%)   ← 그나마 학원 아이디 확인·공공근로 문의
```

**모델은 정당한 금융 아웃바운드 통화를 사실상 본 적이 없다.** 학습 분포가 "기관이 먼저
걸어와 돈 얘기를 하면 204:6으로 피싱"이라고 말하고 있다.

### 어려운 정상 통화 20건 — 오탐률 0.0% → 10.0%

그래서 은행·카드사·보험사가 **먼저 걸어온 정상 통화** 20건을 만들어 걸었다
(`eval/hard_normal.jsonl`, 재현은 `python3 src/eval_hard_normal.py`).

```
  대출 심사 결과 통보     97.8   ← 오탐
  카드 한도 상향 안내     96.3   ← 오탐
  퇴직연금 상담          51.0
  대출 중도상환 회신      43.1
  대출 만기 안내         41.1
  전세자금대출 서류       27.0
  …
  자동이체 변경 안내       0.1

  20건 중 2건이 70점 초과 — 오탐률 10.0%   중앙값 14.3
```

오탐 2건이 하필 **대출 관련 아웃바운드**다. 진단한 구멍의 좌표와 정확히 일치한다.

> **이 20건을 성능 근거로 쓰지 말 것.** 모델이 무엇으로 학습했는지 아는 쪽이 문장을 지었다.
> 용도는 구멍의 크기를 보는 눈금과, 학습셋을 보강했을 때 비교할 기준선 두 가지뿐이다.

### 확률 양극화 — 원인은 "통화 전체를 봐서"가 아니었다

213건이 전부 `0.01` 아니면 `1.00`이라 "중간이 없다"가 미해결 문제였다. 그동안의 진단은
"검증셋이 통화 전체를 담고 있어 애매할 여지가 없다"였다.

```bash
python3 src/evaluate.py --adapter adapter-gemma4 --prefix 200
```

```
                AUROC    중간 구간(0.2~0.8)   재현율@0.5   오탐률@0.5
  앞 200자      0.9951        7건              95.3%       0.0%
  앞 600자      0.9992        4건              96.2%       0.0%
  전체         0.9996         4건              96.2%       0.0%
```

**기존 진단은 틀렸다.** 앞 200자만 줘도 여전히 107/99로 갈린다. 자르는 것으로는 중간값이
거의 생기지 않는다.

대신 **어려운 정상 통화를 주니 중간값이 바로 나왔다** — 51.0 / 43.1 / 41.1 / 27.0.
그러니 양극화의 원인은 입력 길이가 아니라 **검증셋에 애매한 통화가 없다는 것**이다.
모델은 애매한 입력에는 애매한 값을 낸다.

> **다만 이 결과에는 다른 함의가 하나 더 있다.** 앞 200자면 아직 요구가 나오지도 않은
> 시점인데 AUROC 0.9951이 나온다. 실전에서 통화 초반에 경보를 낼 수 있다는 뜻이기도 하지만,
> 모델이 내용이 아니라 **도입부의 말투·구조**로 판정하고 있을 가능성도 같은 무게로 남는다.
> 어느 쪽인지는 실기기 통화로만 가릴 수 있다.

### 남은 것

**① 실기기 통화** — 위 20건은 지어낸 문장이다. 실제 통화를 녹음해 재야 확정된다.

**② 실전 입력 조건** — 학습·검증이 모두 완결된 전사본이다. 실전은 음성인식이 뱉는
전사본이고 오인식과 끊김이 더 많다. 이제 그 전사도 같은 모델이 하므로, 전사 오류가 판정에
어떻게 번지는지를 한 파이프라인 안에서 잴 수 있다 — 아직 재지 않았다.

**③ 학습셋 보강** — 구멍이 확인됐으니 정당한 금융 아웃바운드 통화를 정상 표본에 넣고 다시
학습하는 것이 다음 수다. 공개 데이터를 찾는 일이 먼저다.

## 진행 단계 — 생성에서 규칙으로 바꿨다

확률이 0/1로만 갈리는 문제를 우회하려고 "사기가 어디까지 진행됐나"를 원본 Gemma에게
물었었다. 설계 근거는 이랬다.

> LLM에게 확률을 물으면 학습으로 점검된 적 없는 숫자가 나오지만, **단계는 사실 관계를
> 읽는 일**이라 모델이 잘하고 사람이 채점할 수도 있다.

**이 주장은 틀렸다.** 단계도 결국 생성이라, "몇 %냐"고 묻는 것과 구조가 같았다.

### 재는 방법부터 만들었다

정답지 없이 고치면 "나아 보인다"에서 멈춘다. 그래서 전사본 **36건을 손으로 채점**해
`eval/stage_gold.jsonl` 에 넣었다 — 무작위 표본이고, **규칙을 만들기 전에** 확정했다.
규칙을 만든 쪽이 채점까지 하면 정답이 규칙 쪽으로 휘기 때문이다. 인용구를 함께 적어
사람이 재채점할 수 있게 했다.

단계 정의도 넷에서 셋으로 줄였다. 옛 1단계(접촉·사칭)는 "사칭했지만 아직 아무것도 안 함"
이라 사용자가 할 행동이 갈리지 않았다.

```
1 압박·유인   겁을 주거나 미끼를 건다          → 끊으면 된다
2 정보·계좌   개인정보·계좌·앱 설치를 요구      → 준 게 뭔지 확인하고 차단
3 이체 지시   송금·입금·현금 전달을 지시        → 지금 당장 멈춰야 한다
```

### 왜 정규식이 통하는가

피싱 탐지에서 정규식이 실패한 이유가 단계에는 적용되지 않는다.

```
피싱 여부   사기범이 트리거 단어를 피할 수 있다   →  정규식 실패 (위 42건이 증거)
단계        "이체해 주세요"를 피할 수 없다        →  피하면 사기가 성립하지 않는다
```

다만 **키워드만 보면 서술문에 헛짚는다.** 그래서 요구·질문 문형을 함께 요구한다.

```
"계좌번호나 비밀번호 이런 거 절대 요구할 수가 없게 돼 있고"
    → 사기범이 "우리는 안 물어본다"고 말하는 중인데 정보 요구로 잡힌다

              키워드만    문형까지
  피싱 706건     81건       46건
  정상 711건      7건        1건    ← 헛짚음 7분의 1
```

정보는 **묻기만 해도** 요구다("잔액이 얼마씩 남으셨죠?"). 돈은 지시해야 움직인다.
그래서 2단계는 질문 문형도 받고 3단계는 지시 문형만 받는다.

### 남은 오답 3건과 한계

```
vishing_529   정답 1 → 없음   STT가 "명의도용"을 "명예조환"으로 옮겼다. 규칙이 못 넘는 벽
vishing_136   정답 3 → 1     "입금을 하시는 방법이" — 지시 문형으로 안 읽힌다
vishing_311   정답 3 → 2     은행 창구 회피 코칭. 사람이 봐도 애매해 정답지에 그렇게 적어뒀다
```

**91.7%는 정답지 36건에 맞춰 조정한 뒤의 값이다.** 조정 전 첫 초안은 77.8%였고, 그때도
생성 모델(33.3%)보다 훨씬 높았다. 조정이 과적합인지 보려고 정답지를 뺀 1,381건에서
분포를 다시 쟀다.

```
  피싱 670건    1단계 347   2단계 163   3단계  58   없음 102 (15%)
  정상 711건    1단계  77   2단계 166   3단계   8   없음 460
```

정상 통화가 3단계로 잡히는 것은 **1.1%**다. 게다가 단계는 위험도 70 이상일 때만 매기므로
정상 통화는 애초에 단계 판정을 거치지 않는다.

**피싱의 15%는 신호가 하나도 안 잡힌다.** 이때 `stage`는 `null`이고, 없는 근거로 1단계를
찍지 않는다 — 그것이 생성 모델이 하던 실수다. 앱은 `주의 필요`로 낮춰 띄운다.

## 참고 — 지어낸 문장으로 해본 것

학습셋 밖 텍스트에 대한 반응을 보려고 통화 4건을 **작성해서** 넣었다. 데이터셋이 아니다.

```
기관사칭(피싱)      99.9  ✓        은행 정기예금 상담(정상)   1.8  ✓
대출빙자(피싱)      99.6  ✓        카드 재발급 안내(정상)     1.6  ✓
```

학습셋의 정상 표본에 금융 통화가 **0건**이라 "금융 어휘=피싱"으로 배웠을 위험이 있었는데,
은행·카드사 통화를 정상으로 판정했다. 키워드가 아니라 구조를 본다는 정황이다.

**다만 이것을 성능 근거로 쓰면 안 된다.** 모델이 무엇으로 학습했는지 아는 쪽이 문장을 지었고,
실제 전사본의 말더듬·중복이 없는 깔끔한 문장이며, 학습 분포 밖 입력에 99.9/1.8이라는 극단값을
내는 것 자체가 ②의 재확인이다.
