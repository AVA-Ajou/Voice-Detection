# Voice-Detection

보이스피싱 탐지 모델의 **데이터·학습·평가**를 담당한다. 안드로이드 앱(`../demo`)과 분리한
이유는 두 작업의 주기가 다르기 때문이다 — 학습은 가끔 돌리는 오프라인 배치이고,
앱은 그 결과물(모델 파일 또는 배점 상수)만 받아서 쓴다.

## 목표

통화 전사본을 넣으면 **위험도와 근거를 함께** 내놓는 모델을 만든다.

```
입력   통화 전사본
출력   {"risk": 87,
        "signals": [{"name":"LAW_ENFORCEMENT","quote":"서울중앙지검 김민수 수사관입니다"}],
        "reason": "위험 — 수사기관 사칭(...), 범죄 연루 주장(...) 정황이 확인됩니다."}
```

앱은 이 출력을 받아 세션에 누적한다. 다채널 융합(통화 위험도를 일정 시간 들고 있다가
문자에서 관련 신호가 나오면 상향)은 학습이 아니라 앱 코드가 담당한다 — 같은 사건의
통화와 문자를 짝지은 공개 데이터가 존재하지 않아서 학습으로는 배울 수 없다.

## 데이터

| | |
|---|---|
| 규모 | 통화 1,417건 (피싱 706 / 정상 711) |
| 형태 | 한국어 전사본. 화자 분리와 타임스탬프 포함 |
| 출처 | 피싱 = 금융감독원 「보이스피싱 지킴이」 공개 녹취 / 정상 = AI Hub |
| 원본 | https://github.com/selfcontrol7/Korean_Voice_Phishing_Detection |

**음성 파일은 없다.** 저장소가 전사본만 공개한다. 금감원 오디오는 원저자에게 요청하면
받을 수 있을지도 모르고, AI Hub 음성은 포털에서 따로 신청해야 한다.

### 커밋하지 않는 이유

코드는 MIT지만 전사본은 제3자 녹취에서 파생된 것이라 재배포가 허용되지 않는다.
그래서 `.gitignore`로 빼고, 저장소에는 **받는 방법과 산출된 숫자만** 남긴다.

## 사용법

**맥에서** — 데이터 준비와 배점 산출까지.

```bash
python3 src/fetch.py                  # 전사본 1,417건 받기 (sparse clone, 약 82MB)
python3 src/build_binary_set.py       # 이진 학습셋 생성 (층화 분할)
python3 src/calibrate.py --derive     # 신호별 배점 — 다채널 갱신에 쓴다
```

**Colab에서** — GPU가 필요한 학습과 평가. 처음이면 [docs/COLAB.md](docs/COLAB.md)를 그대로 따라간다.

```bash
python3 src/train_lora.py                      # Gemma 4 E2B + QLoRA, T4에서 약 1시간 20분
python3 src/evaluate.py --compare-baseline      # 온도 보정 + 신뢰도 검사
python3 src/infer.py --id vishing_38            # 위험도 + 근거 한 건
```

`calibrate.py`는 LLM 없이 데이터셋 전체를 정규식으로 훑어 `log(피싱 출현율 / 정상 출현율)`을
계산한다. 이 값은 이제 학습에 쓰이지 않고, **문자에서 신호가 나왔을 때 통화 위험도를 얼마나
올릴지**를 정하는 데 쓰인다. 로그오즈 공간에서는 그냥 덧셈이 된다 — docs/METHOD.md 6절.

## 위험도 정답을 만드는 방식 — 반드시 알고 쓸 것

원본 라벨은 `0/1` 이진뿐이라 "87점" 같은 정답이 **없다.** 이걸 어떻게 얻느냐가 이 저장소의
핵심 설계 결정이고, 방식을 한 번 갈아엎었다.

**→ 전체 설명은 [docs/METHOD.md](docs/METHOD.md) 를 볼 것.** 그림과 실제 숫자로 따라간다.

### 옛 방식 — 위험도를 우리가 만들었다 (`build_finetune_set.py`)

```
전사본 → 정규식으로 신호 검출 → 신호 무게 합(그룹 상한 적용) → 시그모이드로 0~100
```

학습셋의 위험도가 **관측된 정답이 아니라 우리 공식이 뱉은 값**이라, 모델은 진짜 위험도가
아니라 그 공식을 흉내내는 것을 배운다. 실제로 학습셋 피싱 586건 중 **194건(33%)이 40점
미만**으로 들어가 있었다. 정규식이 대면편취·사채협박 같은 유형을 통째로 놓치기 때문이다.
"피싱인데 안전하다"를 194번 가르치는 셈이라 학습이 성립하지 않는다.

### 새 방식 — 위험도를 읽어낸다

```
전사본 → 모델에게 0/1만 가르침 → 추론 시 P("예") 를 로짓에서 읽음 → 그게 곧 위험도
```

우리는 위험도를 한 번도 만들지 않는다. 0.93은 실제 라벨로 3,600번 손실을 맞으며 조정된
값이고, 검증셋으로 온도 보정을 걸면 **"87점 = 실제로 87% 피싱"이 검증 가능한 주장**이 된다.
근거 문장은 LoRA 어댑터를 끈 원본 Gemma가 원문을 인용해 만든다 — 학습시키지 않는다.

`build_finetune_set.py`는 지우지 않는다. 두 방식을 나란히 비교하는 베이스라인이다.

### 학습이 잘 됐는지 재는 진짜 지표

검증셋 전체 정확도가 아니라 이것이다:

> **정규식이 아무 신호도 못 찾은 피싱 54건**에 모델이 높은 확률을 주는가

준다면 스승을 넘은 것이고, 낮게 준다면 정규식을 복사한 것뿐이라 파인튜닝이 아무 의미가 없다.

## 이 표본의 한계

1. **금융 관련 정상 통화가 없다.** 정상 표본이 일상 대화라 은행·카드사 상담이 빠져 있다.
   그래서 금융 관련 표현이 정상에 0건으로 나와 변별력이 무한대처럼 보인다. 배점 산출에서
   기관 사칭·이체 요구·앱 설치 세 가지를 실측값보다 낮게 눌러 고정한 이유다.
2. **출처와 라벨이 완전히 상관된다.** 피싱은 전부 금감원, 정상은 전부 AI Hub라 녹음 환경이
   다르다. 원저자들은 채널을 맞춘 평가에서 음성 특징 분류기의 오탐률이 1% → 92~100%로
   폭증했다고 보고한다. 텍스트에서도 같은 위험이 남아 있다.
3. **길이 편향** — 피싱 평균 1,674자, 정상 702자. 모델이 길이만 보고 찍을 수 있어
   평가할 때 길이 구간별로 나눠 봐야 한다.
4. **라벨 품질의 천장은 정규식이다.** 피싱 706건 중 54건(7.6%)은 신호가 하나도 안 잡혀
   낮은 점수를 받는다. 모델은 이 유형을 배울 수 없다. LLM으로 일부를 재라벨링해 섞으면
   그만큼 올라간다.
